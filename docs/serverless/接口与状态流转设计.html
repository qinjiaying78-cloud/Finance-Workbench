Finance Workbench 多人协作实施设计

GitHub Pages 提供网页，Supabase 提供登录、账套数据库和同步函数。飞书多维表格是首个外部数据来源。一个账号可兼任多个角色，每笔财务审批仍须由另一名具备总监角色的人员完成。

数据结构角色与数据权限接口契约状态流转飞书同步科目与税务验证与部署

1. 数据结构

下载 PostgreSQL DDL 和 RLS SQL。作为新 Supabase 项目的首次迁移。若上一版设计 SQL 已执行，须另做增量迁移，把旧 book_members.role 写入 book_member_roles，回填历史流程可验证的制单与提交身份，再收紧约束。历史来源无法确认时保留原记录并标记待核对。任何增量迁移应先在备份副本验证。

范围核心表主键与业务约束
账套与成员books、book_members、book_member_roles、reporter_scopes、periods成员唯一键为账套和用户。角色唯一键再加角色。撤销单个角色保留其他角色。账期以月首日期标识。
科目与期初accounts、dimensions、account_dimensions、opening_snapshots、opening_entries、opening_entry_dimensions科目按同账套编码引用父级，账套内编码唯一。辅助核算按客户、供应商、部门、研发项目和银行账户划分。每套账只保留一份首次启用的期初快照。
凭证vouchers、voucher_lines、voucher_line_dimensions凭证号按账套和月份唯一。每条分录只能有一个非零方向，金额以整数分保存。冲销凭证关联原凭证，同一原凭证最多有一张已记账冲销凭证。
外部来源与同步sync_connections、sync_batches、sync_runs、sync_observations、external_rows连接只保存配置和密钥引用。外部基线以账套、连接、记录 ID 为键。批次和扫描暂存不开放给网页。每个连接最多一个正在排队或执行的任务。
台账与差异ledger_items、invoice_followups、match_allocations、reconcile_alerts覆盖仓管、报销、资产、资金。保存业务号、款项性质、发票是否开齐及催票标记、研发项目、数量、金额和税额。锁定原记录的业务字段，财务更正关联原单并另存。催票事件单独留痕。
审批、首页与审计workflow_cases、workflow_tasks、user_preferences、audit_logs、command_receipts每轮审批绑定准确的单据版本。同一单据最多一轮待审批。常用入口按账套和用户保存有序 ID。审计保留时间、操作者、记录标识和前后快照。幂等回执只供命令内部使用。
增值税结转vat_closings按账套、月份、版本保存依据和结果。同月只允许一条有效结转，关联凭证唯一。数据库检查转出金额和留抵金额的计算一致性。

业务主外键带 book_id，禁止跨账套引用。人民币以整数分运算，经 JSON 返回时用字符串保留精度。数量采用定点小数。审计触发器覆盖关键业务变更，数据库普通角色无法改删日志。平台维护账户是受信任管理边界，审计日志用于追溯和核对。

2. Supabase RLS 与角色权限

角色可读范围写入命令实施权限
财务总监本账套财务数据、同步配置、成员和审计记录。流程任务按本人指派展示。个人快捷入口也无法通过审计接口查看。终审、批准结账和解锁、角色和配置管理、授权导出。
会计本账套会计所需数据、对账证据和业务审计记录。成员角色、填报范围和同步配置的审计仅总监可见。制单、维护科目、发起锁定记录更正或红冲、提交审核、处理同步差异、提交增值税和期末结转。
出纳本账套资金台账及被标记为出纳可见的采购、入库、发票记录，以及这些记录的催票事件。收付款登记、相关记录催票更新。生成凭证时由会计接手提交。
仓管／业务填报员仅限本人提交且明确授权的仓管、报销或资产模块记录。新增、编辑本人在授权模块内的草稿，提交报销资料或业务登记。
兼任者已激活角色的可读范围取并集。逐项检验操作所需角色。制单人和提交人即使兼任总监，均无法终审该轮。
  • 网页使用项目发布密钥和用户会话。SQL 按 auth.uid() 检查活跃账套成员及其未撤销角色。匿名用户没有账套读权，登录用户没有对业务表直接写入的权限。发布密钥、用户密钥和后端密钥的权限边界见 Supabase API 密钥文档。
  • 流程读权限要求本人发起或持有有效的本人任务。待办一旦需要某角色，角色撤销后立即从该用户的待办视图移除。读取目标单据仍需通过目标模块的权限。常用模块配置始终仅本人可读，首页会按当前权限过滤已失效的快捷入口。
  • 所有写入由窄权限 RPC 或 Edge Functions 完成。RPC 以会话为准取用户身份，按账套重查角色、范围、记录归属、账期和版本。对授权辅助函数使用固定搜索路径并限制执行权。后端提权角色缺省也没有这些业务表的直接写权限。Supabase RLS 文档
  • 首个总监由项目维护者一次性绑定已有 Auth 用户。之后总监才可管理成员角色和填报范围。角色调整事务保留至少一个活跃总监，撤销后未完成审批重新指派。账套只有兼任会计的唯一总监时，严格终审需要邀请另一人担任总监。

3. 核心接口契约

下表为实现契约。数据库文件包含建表、权限和部分数据库保护，命令及页面由后续实现交付。所有写命令携带 bookId 和 requestKey，变更已有记录另带 expectedVersion。同用户、账套、命令与幂等键使用相同参数时返回原结果，参数改变返回 409。审批、凭证与账期操作采用行锁和版本检查，在同一事务内记录结果、待办及审计。锁冲突和账期状态冲突返回 409，字段错误返回 422，无会话返回 401，越权返回 403，不可见或跨账套记录按 404 返回。

建议接口操作者输入与返回
list_my_books()、get_my_access(bookId)已登录用户返回有效账套、角色、模块范围与 UI 可用操作。
set_member_roles(bookId, userId, roles, scopes)总监事务内增减角色及授权范围，返回实际生效角色。串行化同账套权限设置，避免并发撤销最后一位总监。
save_account、set_account_active、get_trial_balance会计维护，会计和总监查询校验科目编码、层级、启用状态和辅助核算。查询按月、级次和维度返回期初、借、贷、期末。
save_ledger_draft、submit_ledger_item、add_invoice_followup按账套角色和模块范围返回记录 ID、版本及状态。报销由填报人登记，会计核验后发起总监待办。出纳催票追加状态事件。
save_voucher_draft、submit_voucher、reverse_voucher、request_ledger_change会计提交校验分录与账期并返回凭证、审批单和版本。冲销或台账更正提供原记录、原因、变更内容，在目标开放月份走同样的终审链路。
decide_case(caseId, decision, note)指定且独立的总监拒绝须说明原因。批准财务命令后，同一事务内应用业务动作、结束待办并通知发起人。响应返回审批状态、业务状态和凭证号等结果。
save_sync_connection、sync-manual、sync-scheduled、get_sync_run配置由总监负责，手动同步由总监或会计发起，计划同步由 GitHub Actions 发起保存连接映射和启用状态。触发接口返回 202 与运行 ID。进度查询返回开始及结束时间、扫描完整性、新增、成功、异常及重复计数。
record_match、resolve_reconcile_alert、get_audit_diff会计处理，会计和总监核查三单匹配传入三种单据、行号、数量和分摊金额。差异处理说明和证据写入审计，影响既有账目的修改另起审批。比较接口按字段返回旧值和新值。
get_workflow_inbox、mark_workflow_notice_read、set_shortcuts本人按我的待办、我的待阅、我的已办／已阅、我的发起及任务分类、发起人、状态分页。快捷入口为排序后的模块或子功能 ID 列表，保存时检查权限和重复项。
preview_vat_close、submit_vat_close、submit_period_close、request_period_unlock会计发起，总监终审提交时带账期、版本和计算依据摘要。批准时重新核对关账或结转条件。返回审批单、结转金额及适用时的凭证号。

需要用户会话的 Edge Function 应校验 Supabase 会话并在数据库中保留调用者身份。计划入口使用独立的服务凭据、时间戳和请求标识，通过服务端校验后仅处理已启用且勾选定时的连接。GitHub Actions 持有调用计划入口所需的秘密，Supabase 项目后端密钥及飞书凭据留在服务端。Supabase Edge Functions 鉴权

4. 状态流转与终审

业务状态与事务规则
凭证与红冲draft → submitted → approved → posted。批准与记账同一事务，外部读取直接看到最终记账状态。submitted → rejected 后会计另起一轮。提交后冻结内容，审批绑定提交时版本。红冲同侧以负数冲减原额，批准前复核原凭证已记账、开账月份和冲销唯一性。
审批待办会计提交后只向具备总监角色且与制单人、提交人不同的独立账号指派；审批人与提交人由会话获取。找不到独立总监时返回明确原因，原单保留草稿或当前可重试状态。多个总监获派时先提交有效决定的一人完成，其他审批任务同时撤销。驳回保留理由，发起人收到新通知。
外部台账与报销外部行导入时保存只追加基线，创建已锁定的 pending_reconcile 台账。核对通过后进入业务确认或制单流程。报销经会计核验并提交后，由总监批准。已锁定的业务字段通过更正记录或红冲调整，原事实和外部证据保留。新的更正版本仅在应用后成为报表采用的版本。
账期open → review → locked，驳回从 review → open。进入复核后停止本期制单、改账与记账。提交结账前校验试算平衡、未完成凭证、未结业务及适用的税务结转。解除锁定须会计发起、独立总监审批，审批时复核后续期间依赖。未获批期间保持锁定。
差异与催票差异 open → investigating → resolved / dismissed，决定须附理由和证据。催票按 pending → reminded → received → closed 追加事件。属于业务处理的待办可由获授权会计或出纳完成，涉及改账则另走终审。
待阅与历史待阅通过 read_at 进入已阅。已办显示本人实际处理的动作。我的发起保留原提交人和历次状态。角标统计个人待办与未读通知，数据按当前权限实时过滤。

5. 飞书同步、异常与三单核对

  1. 读取与身份识别。 首版通过飞书自建应用取得服务端访问令牌，读取已授权数据表的记录。连接用应用或表格标识配置，逐页用记录 ID 对应账套内外部基线。字段映射版本、币种、金额与小数格式固定；保存受控字段的原值及规范化哈希。飞书多维表格官方说明
  2. 同一同步流程。 网页触发手动同步，GitHub Actions 计划每天北京时间 02:17 调用同一套处理流程。运行分为 queued → running → succeeded / partial / failed。分页处理采用租约、检查点和幂等写入；超时可续跑，前一执行者租约失效后其写入请求应被拒绝。GitHub 定时工作流在默认分支运行，实际启动可能延迟。GitHub Actions 定时触发
  3. 新增与疑似改动。 新记录通过校验且业务键无冲突后插入外部基线和锁定台账，重复扫描同哈希则跳过。既有 ID 的内容改变时生成差异，基线与原台账保持原值。缺失判定要求成功扫完整表，并对候选记录再次验证；分页失败、失去权限或数据范围变化时给出扫描异常，暂停推定删除。表格空间若可配置，填报人员只开放受控的新增入口，服务端的异常检测覆盖管理员改动或删行。
  4. 统计与审计。 批次显示 newSeen（首次看到的外部记录）、inserted（校验成功并写入）、anomalies（去重异常）、unchanged（本次无变化）。按连接、记录和异常规则归并重复发现，更新最后发现时间并保存证据。调整字段映射时先模拟并形成差异预览，历史基线按其版本解释。
  5. 业务交叉核对。 按同账套供应商、采购单号、行号和物料键关联采购单、入库单与发票。按行分摊，支持分批到货、分批开票。事务内累积检查已匹配数量与未税金额，并比较税额、付款性质及发票状态；超限、缺单或字段不同生成待处理预警。
  6. 适配器边界。 适配器约定 checkConnection()、listPage(cursor)、getRecord(id) 和 normalize(raw, mapping)。分页结果包含下一页游标及完整性所需元数据。同步主流程负责哈希、锁定、审计、重试和告警。Google Sheets 后续使用稳定的业务 UUID 列识别记录，行号仅用于定位。

6. 科目余额表和增值税结转

科目编码长度为 4、6、8、10 位。余额表默认展开到三级，可展开四级。查询汇总时先计算各科目的直接期初和已记账发生额，再沿树向上汇总一次。显示全级次时，合计从直接发生额独立计算，避免祖先与子孙重复累计。父科目新增子科目后停止直接新增分录，历史父级余额继续保留并参与汇总。新增和停用即时反映在凭证可选列表，历史科目可以查询。首次启用期初余额前校验借贷合计、辅助核算必填项和重复记录。

首批账套模板拟包含库存现金 1001、银行存款 1002（100201 基本户、100202 一般户、100203 专户）、其他货币资金 1012（101201 外埠存款、101202 银行汇票存款）、其他应收款 1221、其他应付款 2241。应交税费 2221 下依次设应交增值税 222101、未交增值税 222102、预交增值税 222103、待认证进项税额 222104、待转销项税额 222105、应交企业所得税 222106 及附加税明细。222101 下设进项、销项、进项转出、转出未交税和已交税金等。计算按科目业务标签取数，编码可结合历史数据配置。

「税务管理与导航 → 进项与销项期末结转」首版面向一般纳税人。计算依据为本期已记账分录、可抵扣进项净额和上期确认留抵。可抵扣进项包含已转入抵扣部分，扣减进项转出，待认证且尚未转入的金额单列。计算差额为销项净额减可抵扣进项净额再减上期留抵。差额为正时生成借记应交增值税（转出未交增值税）、贷记未交增值税的待审凭证；非正时生成仅确认留抵的审批单。结转单统一在「我的待办」终审；结转凭证随结转审批记账，不走第二条普通凭证审批路径。结果为 posted 或 confirmed_no_voucher。审批重新计算并比较依据哈希，原凭证变化时退回重新提交。更正既往结转要检查后续期间并经审批，保留原版本及冲销关联。正式投用前应结合账套适用准则核对模板和结转口径。财政部《增值税会计处理规定》

7. 验证与部署范围

  • 在本地 PostgreSQL 兼容运行时执行了完整 DDL，覆盖匿名隔离、两个账套、四种角色、多角色叠加和撤权、限制直接写入、外部基线与锁定台账保护、审计日志防改、凭证审批版本、制单人与提交人自审拦截、冒名审批拦截、独立总监任务和增值税结转约束。
  • 正式试点应先在测试环境应用迁移，建立单独的制单账号与终审账号，验证真实 Auth 会话、RLS、RPC 权限、并发审批，以及飞书分页、权限变化和定时同步。测试账套通过后再做旧版本导入映射，并核对期初、凭证和账表。
  • 交付范围包含数据库建表、行级读取权限和数据库约束，以及接口和状态设计。前端、命令 RPC、Edge Function、飞书 API 联调和真实 GitHub Actions 排程待实现与部署。
