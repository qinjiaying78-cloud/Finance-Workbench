1. 整体架构与部署

现有工作台的 initStorage() 先准备浏览器存储，再探测本机 FastAPI。saveRecords()、getAllFromStore() 和 financialBook() 是现有数据入口，界面还有本地期末校验及凭证流程。分阶段保留七个侧栏模块、子菜单和互动导览，新增独立的 Supabase 数据适配层。云协作模式将过账、锁定、报表生成和权限验证交由数据库。云连接断开时停止协作账套写入。离线练习用单独的数据空间。

GitHub Free 的 Pages 通常需要公开仓库。页面、前端代码和项目公开配置可见，账套、业务样例以外的备份、数据库、凭证附件和密钥均不进入 Pages 构建或仓库。采用独立静态构建目录、HTTPS 和受邀登录。GitHub Pages 对商业 SaaS 和涉及敏感交易的网站有限制。若面向客户经营在线财务 SaaS，正式发布前须选符合用途的静态托管，该替换不会改变数据库设计。GitHub Pages 使用限制

2. 数据库与权限

用途表约束与读取范围
账套、成员与账期books、book_members、periods、reporter_scopes角色按账套配置。所有业务对象和关系带账套 ID，复合外键阻断跨账套关联。停用成员后 RLS 即时收回权限。
总账与明细accounts、dimensions、account_dimensions、vouchers 及分录、分录辅助表，opening_snapshots 及期初分录凭证、币种和期初按整数分保存；数量用定点小数。过账时事务核对借贷、科目启停、辅助维度、期间状态、自审及版本。
业务台账ledger_items、match_allocations仓管、报销、固定资产与出纳单据。记录预付款或发货款、发票齐全状态、是否催票、研发项目。按采购单行、入库单行和发票行分配数量与金额。
外部同步与预警sync_connections、sync_batches、sync_runs、sync_observations、external_rows、reconcile_alerts服务侧暂存分页证据，已接受的外部基线禁止修改或删除。来源连接、记录 ID 唯一；重跑不会重复入账。
个人配置与流程user_preferences、workflow_cases、workflow_tasks个人快捷模块按用户与账套存储。流程分申请与任务，用户只读本人参与或发起的流程。源单据跳转仍重新鉴权。
税务与审计vat_closings、audit_logs每账套每期间最多一个有效 VAT 结转版本。事务内审计触发器记录操作者、关联键、时间、请求 ID 及前后快照；日志为追加型。

SQL 已启用 RLS。匿名无数据访问权，浏览器角色仅获必要的读取权限。业务写入 RPC 会逐条授予执行权限，校验 auth.uid() 对账套的当前角色和单据范围，禁止默认 PUBLIC EXECUTE。系统密钥仅在 Edge Function 环境使用。审计追加保护覆盖应用身份和服务身份的正常操作，项目数据库所有者能改变数据库规则。正式运行时将审计摘要和周期快照独立保管。Supabase RLS · 公开与服务密钥的边界

角色权限
财务总监账套业务全查、授权导出、终审、期间锁定或有理由重开、成员与外部连接配置。同一人跨角色也禁止自审。
会计会计凭证与科目维护、核对差异、发起锁定单据更正或红冲、报表与增值税草稿及必要财务导出。终审由另一位授权人员完成。
出纳资金记录与相关采购、收货、发票台账只读。通过专用 RPC 登记资金或提交催票状态，不获得修改总账和已锁定业务凭证的权限。催票动作留痕并在服务侧限制对象和字段。
仓管／业务填报员仅在获授权的仓管、报销或资产模块填报与查看本人的提交记录。业务表单使用专用的项目选项接口，后端按允许的辅助字段返回最小数据集。

附件后续使用 Supabase 私有 Storage bucket，按账套、单据和当前权限签发短时访问链接。SQLite 的附件、库存资产明细、合同、银行对账、工资及其他既有档案需另做迁移映射。上面的首期 schema 覆盖本次六个模块的基础模型；现有全部业务的迁移表与写入 RPC 属于确认后的开发工作。

3. 核心接口与流程

接口契约权限与状态变化
workspace_context()、save_shortcuts(book_id, keys, version)返回可见账套、角色、菜单权限、个人配置。保存校验用户、导航键和版本。操作成功后刷新快捷入口。
submit_ledger_item(...)、update_invoice_followup(...)、request_correction(...)提交进入待核对或待审。账期锁定后停用本期写入。已锁定台账由财务填写原因走更正单，产生关联的新版本或冲销，原凭证与来源证据保留。出纳只调用催票专用入口。
submit_voucher(...)、review_voucher(...)、post_voucher(...)、reverse_voucher(...)草稿 → 待审 → 已审核 → 已记账。驳回留痕后可修订重提。已记账凭证不能直接改分录，红冲应在开放期间生成关联凭证。提交、审批、过账均带版本；写请求带唯一请求键。
lock_period(...)、reopen_period(...)开放 → 待复核 → 锁定。总监在关账前验证试算、银行、业务和税务状态。重开记原因并重跑受影响的报表与税务链。凭证过账、结转和关账竞争同一账期行锁。
save_account(...)、trial_balance(book_id, month, level)财务创建或停用账户，校验父子编码。余额由服务器聚合已记账分录。返回逐行借贷、期初期末、级次、父级与辅助维度下钻数据。
workflow_inbox(...)、workflow_act(...)、mark_notice_read(...)我的待办为本人未处理任务，待阅为本人未读通知，已办与已阅按处理或已读时间，我的发起按本人创建查询。筛选支持类别、发起人及状态。审批必须属于指派且仍有源单据权限；通知只改本人的已读状态。
vat_preview(book_id, month)、vat_create_draft(...)财务从已记账数据预览，再生成待审凭证或确认无需凭证。审批过账后更新月度结转状态。对已有记录幂等返回。快照变动时要求重算。
POST /functions/v1/sync-manual、POST /functions/v1/sync-cron手动由会计或总监指定其获授权账套的连接，验证用户 JWT。定时接口仅持有专用随机密钥的运行器可用，后端只取启用且允许定时的连接。两者共用同步逻辑与连接锁。

业务写入把状态转移、原始单据、任务、凭证与审计日志提交在一个数据库事务内。校验旧版本失败返回 409，界面提示刷新；角色和账套不匹配返回拒绝。第一位总监通过 Supabase 控制台创建 Auth 用户后，由数据库管理员写入 books 与 book_members；后续角色分配走总监专用接口。

4. 外部表格、同步与三单核对

  1. 连接配置绑定账套、来源、表、用途和字段映射版本。总监可管理映射和凭据引用，密钥值从 Supabase Secrets 注入。飞书自建应用通过 tenant_access_token 分页读取并使用稳定 record_id。Google Sheets 用获指定表格读取权限的身份调用 values.batchGet，必须预先提供受保护的稳定 external_id 列。行号、摘要或金额都不作主键。飞书查询与权限说明 · Google Sheets 批量读取
  2. 首期每天做一次完整分页核验，只把新增行写入业务台账。规范化金额为分、数量为定点、枚举为统一值、空值与日期按固定规则处理。基线保留规范化快照、SHA-256、映射版本。可在后续加增量拉取提速，完整核验仍用于发现删除和旧行修改。
  3. 接收到新 ID 先放暂存，发现重复 ID 时把该 ID 整组隔离。完整性确认后，用事务创建外部基线及锁定台账，台账进入「待财务核对」，不会自动过账。相同 ID、相同快照跳过写入。已存在 ID 内容不同，创建「疑似篡改」。完整扫描确认缺行后创建「疑似删除／缺失」提醒。权限变化、分页超时、视图过滤变更或异常空结果时标记扫描不完整，禁止据此判断删除；可要求再做一次独立完整扫描确认缺失。
  4. 单次处理以连接为单位加数据库租约，续跑持相同请求键和租约栅栏。页面显示开始、结束、上次成功及读取、新增、成功、异常数；错误响应不回填历史账。并发手动与定时请求复用或等待在跑连接。失败在租约回收后继续，观察表保留短期以供核对。
  5. 按采购订单号＋行号、供应商、商品、币种和税率匹配。分批到货、部分开票用数量与不含税金额分配行，校验累计不超单。预付款先列为付款阶段，不直接对冲到货数量；发货款按确认收货与发票链核对。把外部金额、数量、款项性质及发票状态和系统账逐项对照，按稳定指纹汇总异常，避免每晚重复发待办。差异弹窗按字段显示前后值与来源。外表的真正「仅追加」由飞书权限或 Google 表保护、专用提交入口实现；有编辑覆写权限的来源系统仍需接受事后核对。

5. 科目、余额表与增值税

代码采用 4／6／8／10 位的项目编码约定，默认展开或查询 1～3 级，可启用 4 级。父级取去掉最后两位后的代码，由复合外键校验。在报表中同时显示「本级直接发生额」与「含下级汇总」。期初按正式启用期余额与前期已记账流水计算，本期借和贷分别向上归并，期末按带符号余额计算后展示借贷方向。合计基于原始分录一次汇总；不再把父级和子级显示金额相加。

6. 首页、待办与前端 SDK 接入

首页压缩 Banner，新增「编辑常用模块」。七个一级入口点击后仍展开侧栏，子功能直接打开现有页。快捷模块可勾选、排序、保存；给键盘移动提供上移与下移按钮。权限变化后在显示和保存时过滤不可访问项。顶栏铃铛分开展示待办和未读数量，从当前账套按人聚合，点击列表进入业务单据。完整「流程中心」分四类视图及已阅／已办细分，可按类别、发起人、状态筛选；切换账套后重载。首版使用分页和有界刷新，避免依赖实时订阅才能获得正确状态。

引入 @supabase/supabase-js，依赖版本和锁文件随静态构建提交，并配置 GitHub Pages 子路径。前端配置只有项目 URL、公开 publishable key 和应用回调地址。首版建议 GitHub OAuth 受邀账号，第三方表格权限仍由服务端独立管理；Auth 注册策略与邀请流程在测试项目先验证。若使用邮件方式，先核对 SMTP 发信限制并配置合适的邮件服务。下列是接入形状，其中 workspace_context 属于下一阶段 RPC。

import { createClient } from '@supabase/supabase-js';
const sb = createClient(projectUrl, publishableKey);

// Redirect 回到页面后：
const { data: { session } } = await sb.auth.getSession();
if (session) {
  const { data, error } = await sb.rpc('workspace_context');

  renderAuthorizedWorkspace(data);
}
// 手动同步按钮点击时：
const result = await sb.functions.invoke('sync-manual', {
  body: { book_id: activeBookId, connection_id: selectedConnectionId, request_key: crypto.randomUUID() }

7. GitHub Actions 配置步骤

  1. 新建 Supabase Free 测试项目，在测试项目运行本包 SQL。创建首个授权身份与账套，检查角色可见性。生产数据迁移前先导出备份，导入临时账套，比对期初、分录、附件和期末报表。
  2. 实际开发并部署 sync-manual、sync-cron 后再启用 workflow。前者验证 Supabase 用户 JWT 和账套角色。后者是专用机器入口，配置该函数的入口以接受自定义机器认证，并在函数首行恒时校验 x-fw-cron-secret，校验失败不查数据库。不要全局关闭 JWT 验证。设置 32 字节随机值，例如由管理员使用密码管理器生成；独立于 Supabase 管理密钥。
  3. 在 Supabase Edge Secrets 配置 FW_CRON_SECRET 及飞书或 Google 只读凭据，后台只选择命名引用和映射。GitHub 仓库打开 Settings → Secrets and variables → Actions，在 Variables 设置 SUPABASE_URL，在 Secrets 设置同值 FW_CRON_SECRET。仓库无需存 Supabase 管理密钥或外部表格凭证。
  4. 把 scripts/sync-nightly.mjs 与 .github/workflows/finance-sync.yml 放入默认分支。首次在 Actions 运行 Finance Workbench nightly sync → Run workflow，确认应出现一次同步、重复运行不覆盖或重复入账。UTC 17 18 * * * 对应北京时间次日 02:17。
  5. Pages 部署只发布构建产物，设置 Supabase Auth Site URL 和允许的精确 Pages 回调。用两账套、四角色、一个外部样表和相同账户不同权限测试；对录入、篡改、删除、部分失效、并发、过账和迁移分别演练后才切换生产。

定时接口约定。 同一 GitHub run ID 使用同一 request_key。POST 小批执行或续跑，返回同一个 sync_batches.id 作为 run_id；单批含各连接 sync_runs，服务器锁定目标连接清单。返回 queued 或 running 时脚本继续调用，直到终态。后端在单次请求超时前返回，下一请求按检查点继续。成功要含 stats: { read, new, success, anomalies }；正常查出业务异常仍可标记同步成功，部分连接技术失败返回 partial。脚本重试临时错误并保持相同请求键，日志只输出编号和统计。交付的 SQL 和脚本可先用本地模拟验收，正式跑飞书或 Google 依赖尚待实现的 Edge 同步服务。

8. 开发顺序与确认点

  1. 先做身份、账套隔离、期初迁移校验、凭证和锁期事务。在测试账套通过跨租户、越权、重复、关账竞争测试。
  2. 再做科目树、已记账余额表、标准报表、审计与流程中心，以现有 11 月演示账套的期末数验证迁移前后账表勾稽。
  3. 接飞书／Sheets，先验证一种再接另一种。验证只增不改、重复 ID、分页遗漏、权限缩小、篡改与删除、三单对照和告警收敛。
  4. 最后接首页偏好、待办提醒和增值税结转。先覆盖一般纳税人简化路径，再核定特殊税务情形。
